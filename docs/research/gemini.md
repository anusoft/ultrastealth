Architectural Taxonomy of Modern Web Bot Detection: Environments, Signatures, and Evasion EngineeringThe technical conflict between automated user agents and web security systems has transitioned from basic heuristic validation to deep execution-environment profiling. Historically, bot mitigation relied on static, single-point checks, such as identifying generic HTTP User-Agent strings, analyzing simple rate-limiting thresholds, or blacklisting known datacenter IP subnets. However, the rise of advanced automation engines—such as Puppeteer, Playwright, Selenium, and their various customized modifications—has forced a shift toward real-time environmental auditing.Modern state-of-the-art bot detection architectures evaluate the integrity of the client’s JavaScript execution pipeline, verify physical hardware features, analyze low-level network characteristics, and track biomechanical interaction behaviors. When evaluating an unpatched Pyppeteer instance on Sannysoft, the platform flags several indicators: the navigator.webdriver flag is set to true, the browser’s plugin list is empty, and the user agent string contains HeadlessChrome.Applying a stealth plugin patches these surface-level attributes. The plugin re-populates the plugin array with standard entries (e.g., PDF Viewer), hides the navigator.webdriver flag, and overrides the user agent to mimic a standard headful browser. While these basic modifications can pass Sannysoft's static checks, they fail against modern web security platforms. These platforms detect subtle execution inconsistencies, such as timing differences, proxy prototype traps, and background process mismatches.Selenium Detector and Script-Execution VerificationThe Selenium Detector target page checks for the presence of Selenium and undetected-chromedriver. Unlike passive fingerprint scanners, this testbed requires active client-side programmatic interaction to complete its evaluation. The page exposes a specific diagnostic flow where the automated client must retrieve an internal token from window.token and an asynchronous token from the promise-based function window.getAsyncToken(). These values must then be injected into input fields (#chromedriver-token and #chromedriver-asynctoken) before triggering a click event on the #chromedriver-test button.This setup tests the boundary between client-side execution and the driver interface. Standard webdriver configurations rely on injecting scripts using driver commands like execute_script and execute_async_script. These injections leave distinct execution traces, such as custom document variables or altered timing structures.While some security developers note that forcing manual console evaluations is not a common production defense because of the risk of false positives on standard user flows, it remains a useful diagnostic tool. Evasion tools, such as the Puppeteer mode in Open Bullet 2 (which relies on the .NET port PuppeteerExtraSharp), modify key properties in the main JavaScript context. They use getter overrides or proxy wrappers to alter values like navigator.userAgent, navigator.platform, and WebGL renderer details.However, Web Workers run in isolated execution contexts and are not affected by scripts injected solely into the main thread.       userAgent: navigator.userAgent,

      concurrency: navigator.hardwareConcurrency
    });
  };
`;

    console.log('Environment spoofing detected via Worker discrepancy.');

Because the worker executes in an unpatched scope, it returns the browser's native values (e.g., a Linux platform value or an unpatched User-Agent). When the detection script compares the worker's native values with the spoofed values on the main thread, the mismatch flags the session as automated.WebGL and WebGPU Hardware ValidationTo prevent websites from identifying a headless browser through default software-renderer signatures (such as SwiftShader or LLVMpipe), stealth frameworks spoof WebGL renderer parameters. If the user doesn't explicitly override the configuration, stealth plugins typically default to common hardware signatures, such as "Intel Inc." as the vendor and "Intel Iris OpenGL Engine" as the renderer.However, this basic spoofing has two major limitations:It only patches the main thread's WebGL context, leaving Web Workers with access to the unpatched graphics card details.It does not modify WebGPU, which is a newer API used for graphics and compute workloads.Modern bot detectors perform cross-API graphics audits. If the WebGL context reports an Intel Iris graphics card but WebGPU queries return Apple Metal parameters, or if the WebGL extension limits do not align with the declared hardware profile, the system flags the client for environmental inconsistency.Dynamic Prototype Auditing and Lie DetectionTo detect when developer tools or automation frameworks attempt to hide flags like navigator.webdriver, platforms like CreepJS audit the integrity of the JavaScript prototype chain. In a standard web browser, native properties are defined as accessor descriptors on the prototype itself, rather than direct properties on the instance.If an evasion script uses a basic override, such as setting navigator.webdriver = false, it changes the property's storage type. Detection engines identify these modifications by checking the property descriptor:JavaScriptconst descriptor = Object.getOwnPropertyDescriptor(Navigator.prototype, 'webdriver');
if (typeof descriptor.get !== 'function') {
  console.log('Prototype Lie Detected: webdriver is not defined as an accessor property.');

If an evasion framework wraps native functions in a JavaScript Proxy to intercept these checks, it introduces a toString serialization leak. Native browser bindings return a specific string representation when audited with Function.prototype.toString.call(). If the evasion script fails to patch this, calling toString on the modified property returns the proxy's internal code rather than the standard native string, exposing the modification.Network-Layer, Cryptographic, and Behavioral DiagnosticsAdvanced bot management platforms do not evaluate client-side properties in isolation. Instead, they correlate these values with network characteristics, cryptographic handshakes, and user behavioral dynamics.Passive Handshake and Protocol ProfilingWhen a client establishes an encrypted connection, it transmits metadata across multiple protocol layers. Modern web application firewalls (WAFs) validate whether these lower-layer characteristics align with the browser profile declared in the application-layer headers.TCP/IP Handshake Auditing: Passive TCP/IP fingerprinting engines analyze parameters within the initial SYN packet, such as the IP Time to Live (TTL), TCP Options, and TCP Window Size. Since these values are set by the operating system kernel, they are difficult to modify from a standard browser sandbox. If a client claims to be a macOS-based Safari browser but its TCP SYN packet aligns with a Linux-based datacenter network stack, the connection is classified as automated.TLS and HTTP/2 Profiling (JA4): The TLS handshake exposes a unique fingerprint based on the client's supported cipher suites, extension arrays, and protocol versions. Similarly, the HTTP/2 layer contains unique fingerprints based on the settings frame, window sizing, and stream priorities. If an automation script runs requests directly via standard HTTP library engines (like Node.js Axios or Python Requests) while spoofing a Chrome user agent, the WAF detects the TLS/HTTP2 signature mismatch and blocks the connection.Cryptographic Automation Signaling: Fingerprint.com Web Bot AuthTo distinguish between automated scrapers and legitimate bots, platforms like Fingerprint.com have introduced the Web Bot Auth (WBA) standard. The request includes specific authentication headers: Signature-Input (defining the components signed, the key ID, timestamps, and a nonce), Signature (the cryptographic signature), and Signature-Agent.When a signed request reaches a WAF using this standard, the system fetches the public key from the bot's directory to verify the signature. If verified, the traffic is classified as an authorized bot rather than suspicious automated traffic, bypassing standard fingerprint challenges.Interaction Telemetry and Biomechanical ModelingWhen a website requires user interactions (such as during login, form submission, or CAPTCHA validation), modern security systems evaluate behavioral telemetry to detect automation.Event Coalescing Analysis: Genuine user interactions generate high-frequency input streams. When a human moves a pointer across the screen, the browser's graphics layer groups these inputs into coalesced events using getCoalescedEvents() to track precise sub-frame updates. Standard automation frameworks often inject synthetic movements directly via CDP commands. Because these synthetic inputs fail to populate the coalesced event stream correctly, the WAF can easily flag the interaction as automated.Bézier Cursor Trajectories: Human mouse movements do not follow straight paths or mathematical lines. Instead, they conform to physical constraints, which are often modeled using Bézier curves with overshoot, correction, and speed variance. Advanced behavioral classification systems score client interactions over time. If pointer paths lack human-like physical variability, the session is flagged.Engineering Design of Modern Anti-Detection and Evasion FrameworksTo bypass advanced environmental auditing, the development of evasion tools has evolved from surface-level JavaScript patching to low-level browser engine customization.Evasion Evolution Path

1. Surface-Level JavaScript PatchingEarly evasion platforms, such as pyppeteer_stealth and puppeteer-extra-plugin-stealth, operate by injecting JavaScript overrides into the browser context. This injection typically runs at the start of page execution using the CDP command Page.addScriptToEvaluateOnNewDocument. These plugins patch basic features, such as removing the navigator.webdriver flag, populating standard plugin profiles, and spoofing WebGL parameters.While effective against older heuristic checks, this approach is easily detected by modern security engines. This is because surface-level patches often fail to protect background threads (like Web Workers) and leave prototype anomalies or timing traces that expose the injected code.2. CDP-Patched AutomationTo address the issues caused by standard CDP instrumentation, developers created tools like Patchright and rebrowser-patches. These utilities modify the core communication layer of automation engines to prevent security scripts from detecting active debuggers.Elimination of Runtime.enable: Standard Puppeteer and Playwright instances call the Runtime.enable and Console.enable CDP domains. This call registers the automation framework with the browser, enabling event tracking but also triggering detectable console serialization events. Patchright patches Playwright's codebase to execute scripts directly within isolated execution contexts, bypassing Runtime.enable entirely.Source URL Masking: When standard Puppeteer evaluates scripts, it appends unique source metadata to the script’s footer (e.g., //# sourceURL=pptr:...). Security engines scan the error stack trace to locate these signature strings. CDP-patched systems remove these default metadata tags and replace them with generic names (like app.js).3. Source-Level Binary ModificationThe limitations of JavaScript-based evasions led to the development of custom, compiled browser engines, such as CloakBrowser. Rather than trying to patch runtime environments using external scripts, these systems compile spoofing behaviors directly into the browser's C++ source code.By modifying the engine's source code before compilation, hardware limits, memory allocations, audio metrics, and GPU profiles are handled natively by the browser. The browser does not require script injections or customized command-line arguments (like --disable-blink-features=AutomationControlled), eliminating the runtime anomalies that security scripts look for.4. Relational Fingerprint ProfilesA major weakness of many custom environments is the use of randomized, unsynchronized fingerprints. Evasion tools often generate profiles by randomly pairing device attributes—such as selecting a macOS User-Agent, a Linux-compatible WebGL renderer, and an unaligned hardware concurrency limit. This creates inconsistencies that are easily identified by statistical analysis.The Mochi framework address this vulnerability by implementing relational profiling. It uses a 48-rule Directed Acyclic Graph (DAG) to generate fingerprints. Under this architecture, every fingerprint variable is derived from a single profile seed, ensuring that all reported hardware and software values are relationally consistent. For example, if a macOS User-Agent is selected, the DAG ensures that all related properties—such as the WebGL engine, the system font list, the screen metrics, and the Web Audio API metadata—are mathematically consistent with a genuine macOS device.Comparative Overview of Evasion Tools and Custom RuntimesThe table below provides a detailed structural comparison of modern anti-detection frameworks, mapping their core engines, integration models, and operational limitations.FrameworkExecution InterfaceCore Stealth StrategyScript-Injection footprintKey Structural ConstraintsPatchright[cite: 59, 61]Node.js / Python wrapper over custom Playwright.Eliminates default CDP debugger signaling.Runs user code inside isolated execution contexts to avoid triggering Runtime.enable.Disables the Console API, preventing standard debugging; requires message-passing bridges to access main-world variables.CloakBrowser[cite: 57]Customized, pre-compiled C++ Chromium binary.Native-level hardware and profile validation.Handles fingerprint spoofing directly within the Chromium source code.High infrastructure compilation cost; custom engine patches must be rebased for each new Chromium release.Mochi[cite: 8]Specialized Bun-runtime execution environment.Enforces relational consistency across fingerprint parameters.Runs a lightweight setup script at the top of the frame using the native fetch pipeline.Tied specifically to the Bun execution ecosystem; can introduce performance overhead during initial frame rendering checks.Undetected Chromedriver[cite: 38, 40]Python Selenium-based custom Webdriver.Patches known ChromeDriver trace artifacts.Automatically patches ChromeDriver's binary file before execution to remove automation variables.Relies on the ChromeDriver interface; can be detected if security scripts actively scan for open debugger ports.ConclusionsModern web bot detection has evolved into a highly integrated, multi-layered auditing pipeline. The client’s network-layer handshake, cryptographic signatures, prototype chain properties, multi-threaded worker scopes, and behavioral telemetry must all align to present a coherent, authentic user profile.
